# ldapbench 測試分析總結（2026-11-18）：RHDS 11 / RHDS 13 / OpenLDAP 2.6

> 對象：關心「查詢延遲」與「寫入延遲」，以及它們如何影響 QPS / RPS / TPS 的使用者。
> 資料來源：四次測試的 `report/report_data.json`、08 基準（fio / 網路）、各 M1 的 PCP 紀錄，以及測試後在 Server 上查到的資料庫設定。
> 標示：**【量測】** = 數據直接顯示；**【推論】** = 依數據與產品設計推得，未另外驗證。

## 1. 總結

1. **查詢延遲（Server 能力）**：
   - OpenLDAP 最低、最省 CPU：每筆查詢的 M1 CPU 約 70 µs，RHDS 約 112～141 µs。
   - RHDS 11 與 RHDS 13 很接近。
   - 無負載單筆查詢時，Server 端處理只有約 0.1 ms，使用者感受到的延遲大部分來自 Client 函式庫與網路。
2. **查詢身分的影響**：
   - **RHDS**：匿名 ≈ 管理者，`bench_reader` 每筆多約 20% CPU、QPS 低 10～15%。
   - **OpenLDAP**：三種身分幾乎沒有差別。
   - 和 ACL 有關，但不是單純「ACL 比較多」（匿名一樣要評估 ACL），細節見 4.3。
3. **短連線**：
   - 成本主要在 TLS handshake 與 Bind。
   - **RHDS 13 的 Bind 很貴**（預設 PBKDF2-SHA512，約 160 ms／次）：用帳號 Bind 的短連線只有約 95 QPS，匿名約 1,900 QPS。
4. **寫入延遲**：
   - 同時有 40 個寫入者時，RHDS 11（BDB）的吞吐量約為 RHDS 13 / OpenLDAP（LMDB）的 2.7 倍（約 1,000 vs 345～400 ops/s），延遲約為 1/3（p50 36 ms vs 105～116 ms）。
   - 但**單筆、沒有並行時三者相近**（每次 Modify 約 3～3.7 ms）。
   - 差距來自「並行寫入時能不能合併落盤」：
     - BDB 每筆寫入只需約 1.6 次 I/O、10 KB；
     - LMDB 寫入一次只能一筆，每筆約 10～12 次 I/O、40～49 KB，而且要等 fsync。
5. **複寫**：
   - 無負載時 M1 → M2 的複寫延遲只有幾 ms。
   - 寫入滿載時三套產品的 M2 都跟不上，負載停止後還要數十秒才追上。

## 2. 08 測試前基準（硬體）

- **【量測】fsync 延遲三台接近**（約 0.92～0.97 ms，337～482 次/秒）。這是**每次寫入必須等待的最小單位**，決定了「一次只能 commit 一筆」的資料庫最多能做多少寫入。
- **【量測】RHDS 13 M1 的隨機讀（24.5k IOPS）與循序寫（286 MiB/s）約為其他兩台的 40～50%**。M2（rhds13-m2）的隨機讀 30k、循序寫 348 MiB/s，也偏低。
- **【推論】** 讀取都在記憶體，RHDS 13 磁碟較慢對 R1～R3 幾乎沒有影響。寫入時有影響的是 fsync 延遲，而這項三台差不多，所以 RHDS 13 寫入較慢**不能歸因於它的磁碟**（見第 6 節）。
- **【量測】網路**：
  - Client → M1 的 ping 約 0.2～0.3 ms，單筆查詢的網路 RTT（26）約 0.16～0.25 ms，三套環境相同。
  - 08 的 TCP connect 欄位，RHDS 約 12～19 ms、OpenLDAP 約 2 ms，但 R3 實際量到的 connect 只有 0.27～0.37 ms。08 這一欄是工具層級的量測，不適合用來比較產品。

- **【量測】** 沒有負載時，Server 處理一筆查詢只要約 0.1 ms，三者差距在 0.05 ms 以內。
- **【量測】** 單筆延遲約 1.0～1.2 ms，其中 **Client 函式庫（Python ldap3）占 60～70%**。
- **【推論】對使用者的意義**：低負載下的查詢延遲主要由 Client 端決定（程式語言、函式庫、是否重用連線）。Server 之間的差異要到有並行負載時才會顯現（第 4、5 節）。

## 4. R1 / R2 / R3：查詢

### 4.1 R1 SSSD 查詢（`getent passwd` / 登入類行為）

| 首次查詢 p50（ms） | RHDS 11 | RHDS 13 | OpenLDAP |
|---|---|---|---|
| 測試一 匿名 | 20.08 | 19.74 | 19.68 |
| 測試二 管理者 | 19.83 | 19.78 | 19.66 |
| 測試三 bench_reader | 20.89 | 21.20 | 20.91 |
| 測試四 bench_reader | 21.60 | 21.27 | 20.61 |

- **【量測】** 首次查詢（SSSD 快取 miss）的吞吐量在所有測試、所有產品都是約 **1,650～1,666 次/秒**。M1 CPU 只有 3～9%，Client CPU 約 22～27%。
- **【推論】** R1 的瓶頸在 Client 端的 SSSD（`sssd_be` 單一 thread），**這個測項分不出 Server 差異**。三套產品對「系統登入、id 查詢」的使用者體驗相同，約 20 ms（主要是 SSSD 本身的處理）。
- **【量測】** 用 `bench_reader` 時每筆約多 1 ms，可能是 SSSD 使用 Bind 過的連線與 Server 端 ACL 評估（見 4.3）。
- **注意**：「成功 QPS（含重複）」從 21～24 萬降到 10～18 萬，但這是首次查詢稍慢、較晚進入 SSSD 快取命中造成的，**不代表 Server 容量下降**，請以首次查詢為準。

### 4.2 R2 直接 LDAP 查詢（應用程式 / 連線池，ldap3 長連線）

| 成功 QPS ／ 首次 p50（ms） | RHDS 11 | RHDS 13 | OpenLDAP |
|---|---|---|---|
| 測試一 匿名 | 29,066 ／ 1.26 | 29,467 ／ 1.34 | 37,399 ／ 0.97 |
| 測試二 管理者 | 30,069 ／ 1.16 | 30,103 ／ 1.53 | 38,155 ／ 0.98 |
| 測試三 bench_reader | 26,342 ／ 1.46 | 26,292 ／ 1.71 | 35,589 ／ 1.02 |
| 測試四 bench_reader | 25,899 ／ 1.34 | 27,480 ／ 1.47 | 35,876 ／ 1.01 |

- **【量測】OpenLDAP QPS 比 RHDS 高約 25～30%，延遲低約 0.3～0.5 ms**：
  - 首次 p99：OpenLDAP 2.1～2.3 ms，RHDS 3.6～6.1 ms。
  - M1 CPU：OpenLDAP 34～35%，RHDS 47～54%。
- **【量測】RHDS 11 與 RHDS 13 的 QPS 幾乎相同**；RHDS 13 首次 p50 稍高（約 0.1～0.4 ms）。
- **【量測】** Client CPU：RHDS 51～55%，OpenLDAP 66～68%（2 vCPU）。
- **【推論】**
  - OpenLDAP 的 Client CPU 較高，表示它的 QPS 已經接近 Client（Python）的上限，真正的 Server 差距比表面數字更大。
  - R3 長連線（較輕的 Client）更能看出 Server 本身的能力，見下節。

### 4.3 R3 長連線（較輕量的 Client，較能看出 Server 能力）

| 指標 | RHDS 11 | RHDS 13 | OpenLDAP |
|---|---|---|---|
| 成功 QPS：匿名 / 管理者 / reader / reader（測試四） | 48,243 / 47,577 / 41,067 / 43,598 | 45,875 / 47,057 / 40,789 / 41,403 | 58,689 / 59,306 / 57,200 / 57,428 |
| 每筆 Search 平均（ms）：匿名 / 管理者 / reader | 0.79 / 0.80 / 0.93 | 0.83 / 0.81 / 0.94 | 0.65 / 0.64 / 0.66 |
| **M1 每筆查詢 CPU（µs）**：匿名 / 管理者 / reader | **112 / 112 / 134** | **122 / 117 / 140** | **69 / 68 / 71** |
| M1 CPU 使用率 | 66～73% | 68～73% | 50～51% |

M1 每筆查詢 CPU = M1 CPU 使用率 × 8 vCPU ÷ QPS。

- **【量測】Server 每筆查詢的 CPU 成本**：OpenLDAP 約 70 µs，RHDS 11 約 112 µs，RHDS 13 約 117～122 µs。OpenLDAP 處理同樣的查詢只用 RHDS 約 60% 的 CPU。
- **【量測】匿名與專用帳號的差異（使用者問的重點）**：
  - **RHDS**：匿名 ≈ 管理者，`bench_reader` 每筆 CPU 多約 **+20%**（112 → 134 µs、122 → 140 µs），QPS 低 **10～15%**。
  - **OpenLDAP**：三種身分差 3% 以內。
- **【推論】為什麼 RHDS 用帳號查詢比較慢**（和 ACL 有關，但不是單純「要評估 ACL」）：
  1. **管理者**：完全略過 ACL，所以快。
  2. **匿名**：雖然要評估 ACL，但 389-ds 對匿名有預先計算的「anonymous profile」快速路徑。所以匿名和管理者一樣快，資料也支持這點。
  3. **一般帳號**（`bench_reader`）：走完整的 ACI 評估，每筆、每個回傳屬性都要比對 suffix 上的 ACI。
  4. **另一個未隔離的因素**：測試三、四之前，suffix 上多了一條 `bench_writer` 的 ACI（為了寫入權限），ACI 數量增加，也可能增加每筆的評估成本。若要分清楚，需要在沒有這條 ACI 的情況下再跑一次 reader 查詢。
- **【推論】OpenLDAP 為什麼不受身分影響、也比較省 CPU**：
  - `olcAccess` 只有 3～4 條簡單規則（`to * by * read`），評估成本很低。
  - OpenLDAP 的 access log 關閉，RHDS 開著（每筆查詢都要寫 access log，雖有 buffer 仍需格式化與鎖定）。**這是比較時對 RHDS 較不利的設定差異**，RHDS 每筆 CPU 有一部分來自記錄 log。
- **【量測】RHDS 11 vs RHDS 13 讀取**：每筆 CPU 只差 5～8%，QPS 差 0～5%。BDB → LMDB 在「全部在記憶體」的讀取情境下沒有明顯差異（RHDS 的 entry cache 讓兩者都直接從記憶體回應）。

### 4.4 R3 短連線（每筆都 Connect → TLS → Bind → Search → Close）

| 指標 | RHDS 11 | RHDS 13 | OpenLDAP |
|---|---|---|---|
| QPS：匿名 / 管理者 / reader / reader（測試四） | 1,949 / 1,839 / 1,754 / 1,734 | **1,914 / 100 / 95 / 94** | 1,140 / 1,153 / 1,149 / 1,136 |
| Bind 平均（ms）：匿名 / 管理者 / reader | 2.6 / 2.7 / 3.0 | 2.2 / **153 / 161** | 2.6 / 2.6 / 2.7 |
| TLS handshake 平均（ms，reader） | 12.7 | 132（CPU 滿載排隊） | **29.3** |
| M1 CPU（reader） | 80% | **99%** | 45% |

- **【量測】RHDS 13 用帳號 Bind 時極慢**：Bind 約 150～160 ms，QPS 從 1,914（匿名）掉到 94～100，M1 CPU 99%。
  - 管理者與 `bench_reader` 一樣慢，已確認兩者的密碼雜湊都是 `PBKDF2-SHA512`，所以這是 **RHDS 13 預設密碼雜湊的成本**，不是管理者帳號特有的問題。
  - 表中 RHDS 13 的 TLS 與 Search 時間（約 130 ms）也變長，是因為 CPU 被雜湊運算占滿而排隊，不是 TLS 本身變慢。
- **【量測】** RHDS 11（PBKDF2_SHA256）與 OpenLDAP（`{SSHA}`）的 Bind 只要 2.6～3.1 ms。
- **【量測】OpenLDAP 短連線受 TLS handshake 限制**：TLS 約 29 ms（RHDS 11 約 12 ms），QPS 約 1,150，但 M1 CPU 只有 45%，所以瓶頸不是 CPU。
  - 先前確認過單一 handshake 時兩者相同，只有並行時 OpenLDAP 變慢。
  - **【推論】** 可能與 GnuTLS 的實作或 slapd 接受連線的方式有關，未驗證。
- **【推論】對使用者的意義**：
  - 每次查詢都重新連線的程式（腳本、cron、沒有連線池的服務），每筆約 20～35 ms，比長連線慢 20～40 倍。
  - 在 RHDS 13 上若用帳號 Bind 會再慢約 20 倍。
  - 建議用長連線或連線池。若必須短連線又要用 RHDS 13，需評估降低密碼雜湊成本（例如調整 PBKDF2 迭代次數），但這是安全性取捨。

## 5. RW1 同時讀寫（測試四；讀 32 個 worker、寫 8 個，分到不同 Client）

- **【量測】讀取幾乎不受寫入影響**：讀取 p50 1.05～1.27 ms，和純讀取的 R2 相近。
  - 讀取在記憶體、寫入在磁碟，兩者互不搶資源。

  - **【推論】** 可能與 RHDS 的 checkpoint、交易 log flush 或 entry cache 置換有關，未驗證。
- **【量測】寫入**：RHDS 11 > OpenLDAP > RHDS 13，和 W1 一致（原因見第 6 節）。
- **【量測】** 專用帳號（測試四）與管理者寫入（write-01）的結果差 5～8% 以內，在誤差範圍附近。

## 6. W1 寫入（測試四；40 個寫入 worker，ldap3 長連線，Modify replace `description`）

| 指標 | RHDS 11（BDB） | RHDS 13（LMDB） | OpenLDAP（LMDB） |
|---|---|---|---|
| 成功 Modify ops/s（測試四 bench_writer） | **1,022** | 345 | 380 |
| 參考：write-01 管理者寫入 | 994 | 364 | 400 |
| 延遲 p50 / p95 / p99（ms） | **36.3 / 57.5 / 71.5** | 115.6 / 129.8 / 154.3 | 104.5 / 128.7 / 151.9 |
| M1 CPU / iowait | 8.8% / 5.8% | 4.3% / 10.1% | 2.1% / 10.9% |
| M1 磁碟 IOPS / 寫入量 / util | 1,682 / 10.2 MB/s / 65% | 3,450 / 13.7 MB/s / 83% | 4,624 / 18.0 MB/s / 91% |
| **每筆 Modify 的磁碟 I/O** | **≈ 1.6 次、10 KB** | ≈ 10 次、41 KB | ≈ 12 次、49 KB |
| 40 ÷ 吞吐量（每筆平均排隊時間） | 39 ms | 116 ms | 105 ms |
| 單筆 Modify、無並行（RL1 的 M1 Modify 平均） | 3.5 ms | 3.7 ms | 3.0 ms |

- **【量測】寫入不是 CPU 問題**：三者 M1 CPU 只有 2～9%，磁碟 util 65～91%、iowait 6～11%。
- **【量測】延遲幾乎等於「並行數 ÷ 吞吐量」**：例如 40 ÷ 380 = 105 ms，對應 OpenLDAP p50 104.5 ms。這表示寫入在排隊、一次處理一筆，**使用者看到的寫入延遲主要是排隊時間**。
- **【量測】單筆寫入時三者相近（3.0～3.7 ms）**，差距只在並行時出現。
- **【推論】為什麼 RHDS 11（BDB）明顯優於 RHDS 13 / OpenLDAP（LMDB）**（使用者問的重點）：
  1. **不是硬碟較好**：
     - 三台 M1 的 fsync 延遲幾乎相同（0.92～0.97 ms），RHDS 11 的 fsync IOPS（482）也只略高。
     - RHDS 11 實際做到 1,022 筆/秒，已經**超過硬碟每秒能做的 fsync 次數**，表示它把多筆寫入合併在同一次落盤。
  2. **是資料庫寫入設計不同**：
     - **BDB**：修改先寫入**循序的 transaction log**，資料頁晚一點由 checkpoint 寫回。多個 thread 同時 commit 時，可以由同一次 log flush 一起落盤（group commit）。
       - 所以每筆只需約 1.6 次 I/O、10 KB；並行越多，每次 fsync 分攤的筆數越多。
       - RHDS 11 的 `transaction-batch-val` 是 0（沒有額外延遲批次），合併是 BDB 本身的行為。
     - **LMDB**：沒有 transaction log，用 copy-on-write B+tree。
       - 每次 commit 要寫入所有被修改到的頁面（entry、各個索引、複寫 changelog），再寫 meta page，並各自 fsync。
       - LMDB **同一時間只允許一個寫入交易**，40 個 worker 只能排隊，每筆約 2.6～2.9 ms（1 ÷ 345～380）。
       - 每筆約 10～12 次 I/O、41～49 KB，寫入放大約為 BDB 的 4～5 倍。
  3. **RHDS 13 比 OpenLDAP 再慢約 10%**（同樣 LMDB）：
     - 每筆 I/O 次數相近，但每筆 commit 稍長。
     - **【推論】** RHDS 每次 Modify 要更新的內容較多：changelog 寫在同一個資料庫、操作屬性（modifyTimestamp、modifiersName、entryUSN 等）及其索引。RHDS 13 的資料庫也比 OpenLDAP 大約 3 倍（582 MB vs 198 MB）。另外 RHDS 13 M1 的磁碟循序 / 隨機效能較差，也可能有小幅影響。
- **【推論】對使用者的意義**：
  - 少量、零星的寫入（例如使用者偶爾改密碼）：三者延遲相同，約 3～4 ms。
  - 大量並行寫入（批次同步帳號、大量密碼重設、IdM 同步）：RHDS 11 的吞吐量約為另外兩者的 2.7 倍。
  - 在 LMDB 產品上，**寫入延遲會隨並行數線性增加**，提升寫入能力最直接的是**降低 fsync 延遲**（較快的儲存、具備斷電保護的寫入快取）。
  - 關閉同步（`durable-transaction off`、`olcDbEnvFlags nosync`）可大幅提升，但斷電時可能遺失最近的寫入，需要評估。
  - 用戶端也可以減少同時寫入的連線數，因為總吞吐量不會增加，只會增加延遲。

### 6.1 寫入時的複寫積壓（W1，測試四與 write-01 結果相同）

| 指標 | RHDS 11 | RHDS 13 | OpenLDAP |
|---|---|---|---|
| 負載期間 M2 寫入量 / util | 4.7 MB/s / 55% | 9.9 MB/s / 60% | **1.4 MB/s / 7%** |
| 負載停止後 M2 仍在大量寫入的時間 | 到擷取結束（約第 100 秒）仍未停 | 到約第 84 秒 | 到擷取結束（約第 100 秒）仍未停，停止後升到約 16.6 MB/s |

- **【量測】** 三套產品的 M2 在 M1 寫入滿載時都跟不上，負載停止後還要數十秒才追上。所以在這段期間，從 M2 讀到的資料可能比 M1 舊數十秒。
- **【推論】**
  - RHDS 的 M2 套用複寫時也是逐筆寫入，同樣受磁碟 fsync 限制，所以落後。
  - OpenLDAP 的 M2 在負載期間 CPU 與磁碟都很閒（util 7%），停止後才大量寫入，瓶頸不在 M2 本身。較可能是 M1 端 syncprov 在寫入滿載時送出變更較慢，或 syncrepl 的套用方式造成；未驗證。
- **建議**：需要「寫入後立即從另一台讀到」的應用，在大量寫入期間要固定讀寫同一台 Server，或在讀取端容忍延遲。

## 9. 比較時的限制與注意事項

- **【限制】Client 端是瓶頸之一**：Client 只有 2 vCPU，ldapbench 是 Python。R1（SSSD）與 R2（ldap3）的數字部分受 Client 限制；OpenLDAP 的 R2 Client CPU 已達 66～68%。Server 的真正上限比表中更高，R3 長連線較接近 Server 能力。
- **【限制】設定差異**：
  - OpenLDAP 的 access log 關閉、RHDS 開啟，讀取 CPU 比較對 RHDS 稍不利。
  - RHDS 11 / 13 的 entry cache 大小不同（2.8 / 3.6 GB），但資料都放得下，影響不大。
- **【限制】測試時間與環境**：
  - 四次測試在同一天不同時段執行，測試四開始前重開過所有主機。測試三與測試四的讀取結果差異在 5% 以內，表示結果可重現。
  - `bench_writer` 的 ACI 在測試三之前才加入，測試一、二沒有這條 ACI（見 4.3）。
- **【限制】只測了 40 個並行寫入**：寫入延遲隨並行數線性變化的結論，是依「延遲 ≈ 並行數 ÷ 吞吐量」推得。若要畫出完整曲線，需要以 1 / 2 / 4 / 8 / 16 個寫入者各跑一次。
- **【限制】RL1 量法不同**：write-01 的 RL1 是舊方式（在 Client 上以 ldap3 查 M2，包含約 2 ms 往返），和測試四的數字不能直接比較。

## 10. 建議的後續驗證

1. **隔離 ACL 的影響**：移除 `bench_writer` 的 ACI 後再跑一次 reader 查詢，並另跑匿名對照，確認 RHDS 一般帳號多出的 20% CPU 是來自完整 ACI 評估，還是 ACI 數量增加。
2. **RHDS access log 的影響**：RHDS 關閉 access log 再跑 R3 長連線，讓讀取比較的條件和 OpenLDAP 一致。
3. **寫入並行曲線**：W1 以每台 1～2 個 worker（共 1～8 個寫入者）各跑一次，確認 LMDB 延遲隨並行數線性增加、BDB 增加較慢。
4. **耐久性取捨**：在測試環境比較 `durable-transaction off`（RHDS）與 `olcDbEnvFlags nosync`（OpenLDAP）的寫入能力，作為「是否值得以耐久性換寫入速度」的參考（不建議直接用於正式環境）。
5. **寫入負載下的複寫延遲**：W1 同時開啟 RL1 探測（`-e bench_rl1_probe=true`），量化 6.1 的複寫積壓。
6. **RHDS 13 的密碼雜湊**：若應用程式必須用短連線，評估調整 PBKDF2 迭代次數或改用其他雜湊對 Bind 成本的影響（需配合資安政策）。
