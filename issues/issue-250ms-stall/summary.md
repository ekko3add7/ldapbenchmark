## 問題描述

在 RHDS 13 與 OpenLDAP 的效能比較測試中，觀察到 **RHDS 使用單一連線、循序執行 LDAP 查詢時，少數請求會出現約 250 毫秒的固定延遲**。

測試環境使用 `389-ds-base-3.3.0-5.el10_3`，資料庫包含 10 萬筆使用者資料，資料已載入 entry cache，並已建立相關查詢索引。用戶端透過同一條連線執行使用者查詢，每次收到前一筆 `SearchResultDone` 後，才送出下一筆請求；測試期間伺服器沒有其他負載。

主要觀測結果如下：

- 正常請求約需 **0.2～0.4 毫秒**，約 **0.1%～0.3%** 的請求則需 **250～252 毫秒**。
- 延遲發生在伺服器開始處理該筆查詢之前；查詢開始後，access log 記錄的 `wqtime`、`wtime`、`optime` 與 `etime` 仍低於 1 毫秒。
- 透過遠端 LDAPS、本機 LDAP、LDAPS 及 LDAPI 均可重現；使用標準 `ldapsearch -f` 與不同用戶端程式也有相同現象。
- 關閉 access log 後仍可重現；增加 listener 數量也未消除問題。
- 相同用戶端與查詢條件下，OpenLDAP 未觀察到相同的固定延遲；RHDS 11 則也觀察到類似現象。

雖然發生比例低，但每次延遲遠高於正常查詢時間，會明顯拉高平均回應時間，並增加循序查詢的總執行時間。例如，本機執行 10,000 次查詢約需 6.1 秒，其中約 3.5 秒耗費在這類等待。因此，這項現象會影響單一連線循序查詢的效能表現，以及 RHDS 與 OpenLDAP 的測試比較結果。

## 分析說明

### 1. 工程師確認，現象符合 poll 連線監聽機制中的競態條件

工程師依據 `389-ds-base-3.3.0-5.el10_3` 原始碼檢視後，確認原先提出的流程大致正確，並進一步限縮競態發生的時間範圍。

工作執行緒讀取請求後，會先將連線恢復為可讀取狀態，並呼叫 `signal_listner()`，通知負責該連線的 ct-list 執行緒重新建立 poll 監聽集合。這個通知發生在查詢正式執行之前，因此，**監聽集合重建與該筆查詢的執行會同時進行**。

若重建當下，工作執行緒正持有該連線的 `c_mutex`，ct-list 執行緒的 `pthread_mutex_trylock()` 就會回傳 `EBUSY`，並略過該連線，使它未被加入這一輪的監聽集合。一般連線在作業結束時，通常不會再次發出喚醒通知；若沒有其他喚醒事件，就可能等到 **250 毫秒的 poll timeout** 後，才重新建立集合並讀取下一筆請求。

對應流程如下：

```text
工作執行緒讀取第 N 筆請求，恢復連線可讀狀態並通知 ct-list
    ↓
ct-list 重建監聽集合，與第 N 筆查詢的執行同時進行
    ↓
重建時遇到 c_mutex 忙碌，該連線被略過
    ↓
第 N 筆作業完成，一般路徑未再次通知 ct-list
    ↓
用戶端收到結果並送出第 N+1 筆請求，但連線尚未納入監聽集合
    ↓
約 250 毫秒 timeout 後重新建立集合，才開始處理第 N+1 筆請求
```

工程師特別指出，觸發條件並非工作執行緒「任何時候持有鎖」就會造成延遲，而是**這次關鍵的監聽集合重建，恰好碰上工作執行緒持有 `c_mutex` 的區段**。其中，作業結束時移除 operation、檢查緩衝資料等處理區段，是較大的競態窗口。

此外，依工程師檢視，signal pipe 的處理順序沒有遺失喚醒通知的問題；關鍵在於連線重建時被略過，之後缺少再次重建的觸發。

### 2. 既有測試證據與此機制一致，但尚未直接追蹤到競態事件

這個機制可以合理解釋目前的觀測結果：

| 觀測結果 | 與程式碼機制的對應 |
|---|---|
| 延遲集中在 250～252 毫秒 | 與固定 250 毫秒的 poll timeout 一致 |
| 用戶端等待很久，但查詢本身的計時低於 1 毫秒 | 等待發生在請求被讀取並進入作業處理之前 |
| LDAP、LDAPS、LDAPI 都可重現 | 符合共用連線監聽路徑的問題特徵 |
| 第二條連線持續送出流量時，延遲大幅減少 | 額外活動提供更早喚醒及重新處理連線的機會 |
| 關閉 access log 無法消除延遲 | 不支持 access log 寫入或輪替是主要原因 |

目前已有實測資料與工程師的程式碼分析支持這項判斷，但**尚未透過執行期追蹤，直接捕捉同一次延遲中的 `trylock` 失敗與後續 poll 等待**。因此，可將其描述為工程師確認與程式碼機制相符的競態分析，尚不宜寫成已完成直接追蹤驗證的 RCA。

### 3. 作業結束已有條件式通知，但未涵蓋一般連線的情境

工程師指出，程式碼在作業結束時已有 `signal_listner()`，但它受 `need_wakeup` 條件控制。一般連線通常維持 `need_wakeup = 0`，因此不會執行這段通知。

此外，這個既有通知是在仍持有 `c_mutex` 時呼叫，之後才釋放鎖。因此，不能僅以「作業結束已有通知」判定問題已被處理；仍需由開發團隊評估通知條件與鎖定順序。

目前使用 `trylock`、遇到忙碌連線就略過的設計，源自過去為避免 connection mutex deadlock 所做的修正，其假設是 listener 可以在下一輪再處理該連線。依工程師說明，這是既有設計下被接受的副作用，並非刻意讓請求等待 250 毫秒的延遲策略。

相關歷史議題：[Deadlock on connection mutex，Issue #1672](https://github.com/389ds/389-ds-base/issues/1672)。

### 4. 目前未提供可完全消除問題的受支援設定

依本次工程師回覆，250 毫秒的等待時間沒有對應的 `cn=config` 屬性可調整。已測試的 turbo mode 與 listener 數量設定，也都無法完全消除問題。

[Nunc Stans Support in 389 設計文件](https://www.port389.org/docs/389ds/design/nunc-stans.html)，作為既有連線監聽架構的背景說明。
該文件記載，傳統 `poll()` 主迴圈會在每次呼叫前，巡覽連線清單並重新建立監聽集合，再以 **250 毫秒 timeout** 等待事件。
文件也說明，這種反覆巡覽連線的方式在大量連線情境下有擴展性限制，因此提出使用支援 epoll 等事件機制的 Nunc Stans 框架。

這份文件可佐證 **250 毫秒 timeout 是既有 poll 架構的一部分**，但沒有直接描述本次 `c_mutex` 競爭導致連線被略過的完整競態流程，因此應作為架構背景資料，而非本次問題已被正式記錄或修正的證據。
可維持預設的 **turbo mode 開啟**。本次測試中，開啟時的延遲發生率大致較低，但各組測試有波動，不能視為固定改善幅度或保證。增加背景查詢雖可降低測試中的延遲，也僅能作為診斷證據，尚不能視為工程師確認的正式解法。

工程師另提供下列 upstream 議題作為相關開發方向：

- [EPOLL by default，Issue #7704](https://github.com/389ds/389-ds-base/issues/7704)
- [epoll: connection listener performance and correctness，PR #7983](https://github.com/389ds/389-ds-base/pull/7983)
- [epoll: let idle worker threads wait on epoll directly，PR #7989](https://github.com/389ds/389-ds-base/pull/7989)

**本次回覆尚未確認特定 RHDS 版本已修正此問題，也未確認 epoll build 可完全避免此現象。** 依工程師回覆當時的資訊，開發團隊對於是否預設啟用 epoll 仍未達成共識。

### 5. 後續驗證需使用 OS 層級追蹤

依工程師說明，目前沒有可直接呈現這項競態的 RHDS log level、access log 欄位或內部 trace point。若需進一步完成原因驗證，可與支援及工程團隊協調，以 OS 層級工具追蹤相關執行緒：

- 使用 `perf` 分析 ct-list 與 worker 的執行路徑。
- 使用 `bpftrace` 的 userspace probe 觀察 `pthread_mutex_trylock()` 的回傳結果，並搭配 `strace -T` 觀察 `poll()` 等系統呼叫的等待時間。`pthread_mutex_trylock()` 是使用者空間函式，不能只靠 `strace` 直接觀察其每次呼叫與結果。
- 將追蹤結果與用戶端延遲、access log 時間對齊，確認連線被略過後，是否確實等待至下一次 timeout 才被處理。
